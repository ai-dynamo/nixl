NIXL × CuTe: the API review map

Expose native NIXL operations inside a CuTe compute kernel. Keep host setup in NIXL and completion policy in the application.

Motivation: initiate KV-cache transfer where data is produced or transformed. Packing or compression may justify fusion later; this proposal does not implement a codec, attention integration or an EP runtime.

Scope: NIXL 349514f; NCCL CuTe sources 12df1a1. The table separates native capability from this prototype's coverage; it is not a parity checklist.

2. Symmetry and elasticity: the useful distinction

NCCL GIN does not require symmetric traffic. Its CuTe example has rank 0 issue a PUT and rank 1 wait. Collective setup must not be confused with collective data movement.

Who establishes communication?Agents exchange metadata, connect to individual peers, and prepare views. No fixed all-ranks communicator is imposed by this binding.Communicator, registered-window and device-communicator lifecycle. Window registration and device-communicator creation are collective.

3. What reviewers should decide

  1. API contract: names, request storage/ownership, null-request behavior, progress and publication rules. No NIXL semantics should be invented in the wrapper.
  2. Binding scope: is the three-operation core enough for first review, or should mapped-pointer access be included? Is source-matched bitcode an acceptable initial integration route?
  3. Qualification next: inter-node GPU RDMA, outstanding-request overlap, controlled peer/view replacement, then comparison with native CUDA at matched geometry and transport.

Not claimed: measured zero overhead, speed-of-light throughput, general inter-node support validated here, live in-flight elasticity, or production packaging. NIXL EP v2 is a separate product/API effort, not an “example” supplied by this PR.

Start the implementation review at the Python operations, then the native shim, then the separate example.
